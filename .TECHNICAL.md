# Signal Board — technical overview

Companion to [`.ELI5.md`](./.ELI5.md) (plain-English version) and
[`README.md`](./README.md) (setup instructions). This one's the "how it
actually works" reference.

## Stack

Next.js 14 (App Router, `runtime = "nodejs"`) · React 18 · TypeScript. No
database. No cache layer (Redis/etc.) — removed when the app moved off
TMDB, because the remaining data sources don't need one (see below).

## Data sources, and why there are three of them

| Source                       | What it provides                              | When it's fetched                                                            | Cost model                                       |
| ---------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------ |
| IMDb non-commercial datasets | title, type, year, genres, rating, vote count | Baked once by `scripts/build-imdb-data.mjs`, bundled as `lib/imdb-data.json` | Free, no key, no rate limit — it's a static file |
| OMDb                         | one-sentence plot                             | Live, per request, only for the ~10 titles being returned                    | Free tier, 1,000 req/day                         |
| Watchmode                    | which UK streaming service a title is on      | Live, per request, only for the ~10 titles being returned                    | Free tier, ~1,000 req/month                      |

The IMDb piece is a bulk snapshot because there's no live "discover" API for
it — you either download the flat files or you don't have the data. OMDb
and Watchmode are the opposite: neither supports bulk/discovery queries at
all (title/ID lookup only), and their free tiers are far too small to
backfill 60k+ titles, so they're only ever called for whatever's actually
on screen, never proactively.

## Request flow

```
Browser (components/SignalBoard.tsx)
   │  POST /api/board  { mediaType, sortBy, docsOnly, popularWindow, offset }
   ▼
app/api/board/route.ts
   │  validates/defaults each field, then:
   ▼
lib/board.ts — fetchBoard()
   │  1. filter lib/imdb-data.json by mediaType (+ genre if docsOnly)
   │  2. rank (see "Ranking" below)
   │  3. slice [offset, offset+10]
   │  4. Promise.all([ fetchPlots(ids), fetchTopServices(ids) ])
   ▼
{ titles: Title[], hasMore: boolean }
   ▼
rendered into the list, "Load 10 more" bumps `offset` by 10 and appends
```

Every control change (TV/Films, Rating/Popular, duration window, Docs)
calls `load()`, which increments a `runId` ref and replaces the list from
scratch at `offset = 0`. "Load 10 more" calls `loadMore()` instead, which
keeps the same `runId`, fetches at `offset = titles.length`, and appends —
if a filter changes while a `loadMore` request is in flight, the stale
response is dropped by comparing `runId` on return (see `SignalBoard.tsx`).

## Ranking logic (`lib/board.ts`)

**Rating mode:** sort by `averageRating` desc, tie-broken by `votes` desc.
Filtered to `votes >= 10,000` first — the dataset's own build-time floor is
only 1,000 votes, which still lets a niche title with a small, enthusiastic
fanbase post a 9+ average. 10,000 pushes the list toward things people have
actually heard of. Falls back to the unfiltered pool if that floor leaves
fewer than 10 results (e.g. a thin slice like Docs + a rare genre
combination).

**Popular mode:** sort by `votes` desc (used as a popularity proxy — IMDb's
dataset has no real trending/engagement signal). Filtered to titles whose
`year` falls inside the selected window first. The window is year-only
because that's all the dataset has — no month/day, so "last week" or "last
month" genuinely can't be built from this data; the options are This year /
Last 2 / 5 / 10 years / All time. Same &lt;10-results fallback as above.

**Docs mode:** an additional `genres.includes("Documentary")` filter,
composable with either sort mode.

**Default on load:** Popular + This year (set in `SignalBoard.tsx`'s
initial `useState` calls and the mount `useEffect`).

## The two live-fetch clients

`lib/omdb-client.ts` and `lib/watchmode-client.ts` follow the same shape
deliberately:

- A `Map<id, result | null>` module-level cache, alive for the life of the
  server process (or, on serverless, one warm instance — see caveats).
- One exported `fetchX(id)` and one `fetchXs(ids[])` that just
  `Promise.all`s the singular version.
- Missing API key, non-200 response, or any thrown error all collapse to
  `null` — never an exception that would fail the whole board. A missing
  plot or service flag is a degraded-but-fine result, not an error state.

**Watchmode specifics:** `GET /v1/title/{imdbId}/sources/?regions=GB`
accepts the IMDb ID directly — no separate search/lookup call needed.
Response is a flat array of `{ name, type, ... }` sources (`type` is
`sub` | `free` | `rent` | `buy`). `bestLabel()` keeps only `sub`/`free`
entries (rent/buy isn't "streaming"), then walks a fixed, hand-ordered
`PRIORITY` list of regexes (Netflix → Prime Video → Disney+ → BBC iPlayer →
...) and returns the label of the first one that matches something in the
title's source list. This is **not** a measurement of which platform a
title is most popular on — no API tracks that — it's "of the services this
happens to be on, which is the most well-known one."

## Build script (`scripts/build-imdb-data.mjs`)

Streams (not loads-fully-into-memory) `title.ratings.tsv.gz` (~1.7M rows)
into a `Map<tconst, {rating, votes}>`, then streams `title.basics.tsv.gz`
(~12.7M rows), filtering to `titleType` in `{movie, tvSeries,
tvMiniSeries}`, non-adult, with a joined rating and `votes >= 1,000`. Result
(~61k rows as of the last run) is sorted by votes desc and written as
`lib/imdb-data.json` (~7.7 MB). Run via `npm run build:imdb`; nothing
downstream depends on when it was last run except data freshness — there's
no cron or build-time hook triggering it automatically.

## Deployment model

Static IMDb JSON is committed to the repo (not gitignored, not
regenerated at build time) and bundled into the `/api/board` serverless
function. `OMDB_API_KEY` / `WATCHMODE_API_KEY` are optional env vars —
without them, the respective client's `fetchX` short-circuits to `null`
immediately, degrading gracefully rather than failing.

**Caveat for serverless:** the in-memory caches in `omdb-client.ts` /
`watchmode-client.ts` only persist within a single warm Lambda/Edge
instance. On Vercel, infrequent traffic (this app is used a few times a
week) means most requests hit a cold instance anyway, so the cache mostly
helps within one visit (e.g. across a "Load 10 more" click), not across
visits. That's fine at this usage volume — nowhere near either API's free
tier — but worth knowing if usage ever scaled up.

## Known architectural seams

This app went through a full pivot mid-build: it originally used TMDB for
everything (discovery, ratings, posters, watch-provider data), which was
ripped out entirely in favor of IMDb's bulk dataset. The Watchmode
integration exists because dropping TMDB also dropped platform-availability
data, and that came back later, via an entirely different API, as a
narrower feature (one flag, not full availability lists, one region only).
If you're auditing this codebase: that's why there are two structurally
identical but separate API client files instead of one shared "external
enrichment" abstraction, and why the README's caveats section is as long as
it is.
